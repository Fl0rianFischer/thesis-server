# morning-briefing

Two market briefs, generated by Claude Code running headless on a server and
emailed before you read them.

**The morning briefing**, daily at 5am Jakarta time — about two hours after the
US close, so the overnight session and any after-hours earnings are already in
it. Covers macro, news per holding, upcoming earnings, and reviews of earnings
that just landed.

**The opportunities brief**, Monday and Thursday at 7am — long-horizon buying
candidates. Deliberately slow: nothing in it should matter more today than on
Thursday. Off by default; see [The opportunities brief](#the-opportunities-brief).

Each reads its own past briefs so it doesn't repeat itself. No database, no
backend, no API bill — both run on one Claude subscription via a long-lived
OAuth token.

## How it works

```
push to main  →  GitHub Actions  →  GHCR image  →  ssh deploy  →  /opt/briefing

host cron (every 15 min, one line per agent)
        │
        ↓
   tick.sh <agent>  →  is it this agent's hour and day in $TZ?
                    →  is today's brief already written?
                    →  is the other agent mid-run?
                       │
                       ↓ clear
        docker compose run --rm agent <agent>
                    →  claude -p
                    →  data/<agent>/archive/YYYY-MM-DD.md
                    →  Resend  →  inbox
```

**`TZ` is the only timezone in the project.** It sets when each agent runs, what
date its file is named for, the mail subject, and how it describes the market
day. The host's own timezone is never consulted. Moving country is one variable
and a redeploy.

`agents/<agent>/prompt.md` is the system prompt. `watchlist.md` is the holdings,
shared by both. `agents/opportunities/universe.md` is the candidate list for the
second agent. All of it is baked into the image, so changing your holdings is a
commit and a deploy — versioned and revertible like anything else.

`lib/context.mjs` computes the time facts every agent needs — the zone, local
date and time, the file to write — and each agent's own `context.mjs` adds its
framing on top. `lib/run.sh` concatenates prompt + shared + agent-specific at
run time, so no prompt contains a timezone of its own.

`data/<agent>/archive/` on the box is the memory: past briefs that agent reads
before writing a new one. It's a bind-mounted volume, so it survives redeploys.
Losing it means starting cold.

There is no long-running service. The container is ephemeral — cron fires it,
it writes a brief, it exits.

## Two agents, one machine

Both agents ship in one image and run as one Compose service, told apart by the
argument they're invoked with. The rule for what they share:

> Share anything whose divergence would be a bug. Separate anything whose
> convergence would be a bug.

**Shared** — the image and container definition, `watchlist.md`, `TZ`, the OAuth
token, the Resend sender, `lib/` (`run.sh`, `to_html.mjs`, the shared half of
`context.mjs`), `tick.sh`, `healthcheck.sh`, and `data/cron.log`. Two timezones
or two copies of your holdings would be a bug, so there is one of each. One
`run.sh` rather than two copies, because the uid check and the auth-precedence
guard inside it are subtle enough that a second copy would get fixed in one
place and not the other.

**Separated** — prompts, archives, logs, schedules, model and turn budgets,
attempts counters, locks, and mail subjects. The archive split is the one that
matters most: each agent reads its own last few briefs, and sharing that would
feed daily news into the long-horizon agent as if it were prior research, and
long-horizon analysis into the morning briefing. That is the path urgency would
travel between them.

**Split down the middle** — `context.mjs`. The shared half gives every agent the
zone, the local date and the file to write. The morning briefing's own half adds
the session-close countdown ("closed 2.4 hours ago, next opens tonight"); the
opportunities agent's adds how long since its *own* last brief. Handing a
session countdown to a multi-year brief is how it starts reading like a
day-trading note, so that block deliberately does not live in `lib/`.

**The one genuinely shared resource is your usage limits.** Both agents draw on
the same subscription, so `tick.sh` holds a shared lock across any run: if one
agent is working, the other logs and waits for the next 15-minute tick rather
than running alongside it. Being queued is not a failure and does not count
against that agent's retry budget.

## Setup

### 1. Fill in your watchlist

Edit `watchlist.md`. The "Watching for" line under each holding is what decides
whether a story makes the briefing — specific lines produce a signal-dense
briefing, vague ones produce noise. The "Not interesting" section at the bottom
matters just as much. Both agents read this file.

If you're turning on the opportunities brief, also fill in
`agents/opportunities/universe.md` — the themes, candidates and exclusions it
searches beyond your holdings. The scaffold there explains the shape; the
placeholder entries are examples of *form*, not suggestions, and should all be
replaced.

### 2. Try it locally first

See [Testing locally](#testing-locally) below. Do this before touching the
server — the prompt is where the quality comes from, and tuning it through a
cron log is miserable.

### 3. Generate a subscription token

On a machine with a browser (your laptop, not the server):

```bash
claude setup-token
```

It opens the same browser flow as `/login` and prints an OAuth token to the
terminal. It **saves it nowhere** — copy it straight into the
`CLAUDE_CODE_OAUTH_TOKEN` repository secret.

| | |
|---|---|
| **Valid for** | One year |
| **Requires** | Pro, Max, Team, or Enterprise |
| **Tied to** | The subscription of whoever ran the command — it draws on their usage limits |
| **Can do** | Model requests only. No Remote Control, no claude.ai connectors. Locally configured MCP servers still work |

**It expires silently.** Claude Code's "login expires in 3 days" warning fires
only for an interactive `/login`, not for `CLAUDE_CODE_OAUTH_TOKEN`. About a
year from now the briefing would just stop arriving with nothing to explain it.
Set the `CLAUDE_TOKEN_ISSUED` variable to today's date and `run.sh` will warn
you in the logs a month before it lapses. A calendar reminder is worth setting
too.

To rotate: re-run `claude setup-token`, update the secret, bump
`CLAUDE_TOKEN_ISSUED`, redeploy.

> **Never set `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` on the box.** Both
> outrank `CLAUDE_CODE_OAUTH_TOKEN` in Claude Code's auth precedence (#2 and #3
> versus #5), so either one silently moves your runs onto API billing. `run.sh`
> logs a warning if it sees them.

### 4. Configure GitHub

**Secrets** (Settings → Secrets and variables → Actions):

| Secret | What |
|---|---|
| `CLAUDE_CODE_OAUTH_TOKEN` | From `claude setup-token` |
| `RESEND_API_KEY` | Resend API key |
| `SSH_HOST` / `SSH_USER` / `SSH_PRIVATE_KEY` | The box (reused from the old deploy) |

**Variables:**

| Variable | Example | |
|---|---|---|
| `TZ` | `Asia/Jakarta` | **required** |
| `MAIL_FROM` | `briefing@yourdomain.example` | **required** |
| `MAIL_TO` | `you@example.com` | **required** |
| `CLAUDE_TOKEN_ISSUED` | `2026-08-06` (date you ran `claude setup-token`) | |

Everything above is shared by both agents. Everything below is per-agent — the
`BRIEFING_` prefix is the morning briefing, `OPPS_` the opportunities brief.
(They aren't symmetrical because the `BRIEFING_` names predate the second agent
and renaming them would silently reset a running schedule to defaults.)

| Variable | Example | |
|---|---|---|
| `BRIEFING_MODEL` | `sonnet` | |
| `BRIEFING_EFFORT` | `medium` | |
| `BRIEFING_MAX_TURNS` | `40` | |
| `BRIEFING_HOUR` | `5` — hour in `TZ`, not in cron syntax | |
| `BRIEFING_DAYS` | `1-5` — Monday is 1 | |
| `BRIEFING_MAX_ATTEMPTS` | `3` retries before giving up for the day | |
| `OPPS_ENABLED` | `0` — set to `1` to turn the second agent on | |
| `OPPS_MODEL` | `sonnet` | |
| `OPPS_EFFORT` | `medium` | |
| `OPPS_MAX_TURNS` | `25` — deliberately below the morning briefing's | |
| `OPPS_HOUR` | `7` | |
| `OPPS_DAYS` | `1,4` — Monday and Thursday | |
| `OPPS_MAX_ATTEMPTS` | `2` | |
| `OPPS_MAIL_TO` | optional — a different address for this brief only | |

The deploy fails if any **required** value is empty, and if `TZ` is not a real
tz database name. It warns if both agents are scheduled on the same hour (they
won't collide — the second just waits a tick — but it's rarely intended).
Secrets and Variables are separate tabs on the same GitHub settings page —
filling in one and not the other is the easiest way to get a green deploy that
never delivers a briefing.

### 5. Prepare the box, once

```bash
sudo git clone https://github.com/fl0rianfischer/morning-briefing.git /opt/briefing
```

The checkout supplies `docker-compose.yml`, `tick.sh` and `healthcheck.sh` —
everything else ships in the image. Confirm Docker can pull from GHCR
(`docker login ghcr.io` with a PAT carrying `read:packages`, if the package is
private).

**Do not set the box timezone.** It is not consulted. A box in Berlin serving a
reader in Jakarta is fine, and staying that way is the point — `CRON_TZ` is a
vendor extension many cron builds ignore silently, so the schedule is decided
by `tick.sh` reading `TZ` instead of by cron.

The container runs as **uid 1000**, and bind mounts arrive with the host's
ownership regardless of what the image chowned. If the deploy cannot fix the
ownership itself it prints the exact command; run it once:

```bash
sudo chown -R 1000:1000 /opt/briefing/data/morning-briefing /opt/briefing/data/opportunities
```

Skipping this produces the most confusing failure in this system: `claude`
never starts, stdout is empty, and the run looks like the model returned
nothing. `run.sh` now checks for it up front and says so by name.

**Only those two directories.** `data/` is one mount, but `data/state`
(attempts and locks) and `data/cron.log` are written by the *host* — `tick.sh`
and cron's own redirect. A blanket `chown -R 1000:1000 data` hands those to the
container's uid and silently breaks cron's ability to append. `healthcheck.sh`
checks for exactly this.

### 6. Push to main

The workflow builds the image, writes `/opt/briefing/.env`, pulls, and installs
one cron entry per agent. Each is a fixed `*/15 * * * * /opt/briefing/tick.sh
<agent>` — carrying no schedule and no timezone, so there is nothing on the box
left to drift. The schedule lives in `TZ` and each agent's `_HOUR` and `_DAYS`.

Both entries are always installed. A disabled agent is disabled by
`OPPS_ENABLED`, not by withholding its cron line, so turning it on later is a
variable change and a redeploy rather than a crontab edit.

Ask either agent what it intends to do, without doing it:

```bash
/opt/briefing/tick.sh morning-briefing --dry-run
```

```bash
/opt/briefing/tick.sh opportunities --dry-run
```

Then trigger a run by hand to check the whole path end to end — this one does
send the email:

```bash
cd /opt/briefing && ./tick.sh morning-briefing --force
```

## Testing locally

Four rungs, cheapest first. Don't skip to the bottom — each one isolates a
different failure.

### 1. The prompt, no Docker

Fastest loop, and the only one that matters for output quality. Uses your
existing interactive Claude Code login, so no token needed.

Once, to install `marked` for the HTML email step:

```bash
npm ci
```

```bash
set -a; . ./.env; set +a
```

```bash
./lib/run.sh morning-briefing
```

```bash
./lib/run.sh opportunities
```

With `RESEND_API_KEY` empty it writes `data/<agent>/archive/<date>.md` and
stops. Read it, edit the inputs, delete the file, run again. Expect several
rounds — for the morning briefing the "Watching for" lines and the "Not
interesting" list do most of the work; for the opportunities brief it's the
"Would need" lines in `universe.md`.

To see the time framing an agent will be given — and to check how a brief
reframes itself for another timezone before you actually move:

```bash
TZ=Europe/Berlin AGENT=morning-briefing node lib/context.mjs && TZ=Europe/Berlin node agents/morning-briefing/context.mjs
```

The opportunities agent's block should contain no session-close countdown at
all. If it ever grows one, that's the separation leaking:

```bash
TZ=Europe/Berlin node agents/opportunities/context.mjs
```

To iterate without waiting for a full research run, cap it:

```bash
BRIEFING_MAX_TURNS=8 BRIEFING_EFFORT=low ./lib/run.sh morning-briefing
```

```bash
OPPS_MAX_TURNS=8 OPPS_EFFORT=low ./lib/run.sh opportunities
```

**Run the opportunities brief twice in a row.** The second run should report
that nothing changed. If it invents movement instead, the quiet path isn't
working and no amount of tuning elsewhere will fix it.

### 2. The image builds and Claude runs in it

This is where the genuinely unknown parts are: whether Claude Code installs
cleanly, runs as a non-root user, and finds a writable `HOME` in the container.

Needs a real `CLAUDE_CODE_OAUTH_TOKEN` in `.env` — the container can't reach
your host's login. Generate one with `claude setup-token`.

```bash
docker build -t ghcr.io/fl0rianfischer/morning-briefing:local .
```

Then a five-second smoke test that skips the briefing entirely and just proves
the image and auth work:

```bash
docker compose --profile cron run --rm --entrypoint claude agent -p "Reply with OK and nothing else." --model haiku
```

If that prints `OK`, the image, the token, and network egress are all fine. If
it doesn't, nothing below will work — fix it here. (Overriding the entrypoint is
why this needs no agent argument.)

### 3. A real run through Compose

Same command cron will use on the box — the agent name is the Compose command:

```bash
docker compose --profile cron run --rm agent morning-briefing
```

```bash
docker compose --profile cron run --rm agent opportunities
```

**This sends the email.** Unlike a bare `./lib/run.sh`, emptying
`RESEND_API_KEY` in your shell does *not* suppress it — Compose reads
`env_file: [.env]` and the value in the file wins over your environment. To
rehearse the run without mailing anything, override it on the container:

```bash
docker compose --profile cron run --rm -e RESEND_API_KEY= agent opportunities
```

Check `data/<agent>/archive/` for the brief and `data/<agent>/logs/<date>.json`
for the run metadata. This also verifies the volume mount — if the brief lands
inside the container instead, the mount is wrong and every run would start with
no memory.

Then check the ownership split, which one mount makes easy to get wrong:

```bash
ls -ld data/morning-briefing data/opportunities data/state data/cron.log
```

The two agent directories should be owned by uid 1000; `data/state` and
`data/cron.log` should still belong to you.

### 4. The email path

Test it on its own rather than through a full run:

```bash
curl -fsS https://api.resend.com/emails -H "Authorization: Bearer $RESEND_API_KEY" -H "Content-Type: application/json" -d '{"from":"briefing@yourdomain.example","to":["you@example.com"],"subject":"test","text":"hello"}'
```

Most failures here are Resend domain verification, not the script.

To check how the mail will actually look, render a past briefing on its own and
open the result in a browser:

```bash
node lib/to_html.mjs data/morning-briefing/archive/2026-08-06.md > /tmp/preview.html
```

`run.sh` sends that HTML as the message body with the raw markdown as the
plain-text alternative. Gmail displays `text` verbatim, so without the HTML the
briefing arrives full of literal `##` and `[label](url)`. If the render fails,
the run logs a warning and falls back to text — an ugly briefing beats a missing
one.

### Testing the deploy itself

The workflow only runs on push to `main`, so use a scratch branch and
`workflow_dispatch` from the Actions tab to trigger it without merging.

The one thing you can't rehearse locally is cron on the box. After the first
deploy, confirm the entry landed and that the gate agrees with you about when
it will next fire:

```bash
crontab -l | grep briefing-agent && /opt/briefing/tick.sh morning-briefing --dry-run
```

`--dry-run` prints the timezone it is using, the current local time, the
schedule it read, and its decision — which is the fastest way to tell a
scheduling problem from a run problem.

## Design notes

**The agents have no shell.** `--allowedTools` grants `WebSearch,WebFetch,Read,Write,Glob`
and deliberately omits `Bash`. These agents read untrusted web content every
run, so email delivery lives in `run.sh` instead — a prompt injection in a news
article has no shell to reach for.

This is also why there are no market-data connectors. An API for prices and
fundamentals would be the obvious upgrade to the opportunities brief, and it
would mean an API bill, a key on the box, and an MCP server inside the blast
radius of a hostile web page. Both agents research through `WebSearch` and
`WebFetch` alone, on a subscription, and say "unverified" when a number can't be
sourced — which is a more honest failure than a confident figure from a
connector nobody is checking.

**`--bare` is deliberately not used.** The Claude Code docs recommend it for
scripts, but it ignores OAuth credentials and falls back to `ANTHROPIC_API_KEY`
billing, and it strips `WebSearch`/`WebFetch` from the toolset. Both are fatal
here. The cost is that Claude Code auto-discovers `CLAUDE.md`, hooks, and MCP
servers in the working directory and `~/.claude` — keep the box clean.

**Failure is detected by the artifact, not the exit code.** Claude Code reports
in-run failures, including expired auth, as the result on stdout. `run.sh`
checks that `data/<agent>/archive/<date>.md` exists and is non-empty; that's the
real signal. `tick.sh` uses the same file as its idempotency key — if today's
brief exists, today is done — so there is no separate "have I run yet" state
that can drift out of sync with reality. Each agent has its own, so neither can
mark the other's day complete.

**One timezone, and cron is not told about it.** `CRON_TZ` is a vendor
extension; this box's cron ignores it silently, which meant `0 5` was firing at
05:00 in the host's zone and landing mid-morning for the reader. So cron now
runs `tick.sh` on a fixed 15-minute interval and carries no schedule at all,
and `tick.sh` decides using `TZ` from `.env`. The host's timezone became
irrelevant rather than merely correct, which is the difference between a fix
and a thing that has to be remembered. DST is handled by the tz database, so a
zone that observes it doesn't drift twice a year.

The tick costs one bash process per agent every 15 minutes — a container only
starts when it's genuinely time. `flock` keeps a slow run from having a second
one started on top of it, and `_MAX_ATTEMPTS` stops a broken run from retrying
all day and emptying a month of usage limits in one morning. Both are per agent,
so a failing agent can't exhaust the other's retry budget.

**Two locks, doing two different jobs.** The per-agent lock above prevents an
agent overlapping itself. A second, shared lock prevents the two agents driving
the model at the same time — usage limits are the one resource they genuinely
compete for, and two concurrent research runs on one subscription is the thing
to avoid, not two containers. A tick blocked on that shared lock logs and exits
*without* incrementing its attempts counter: being queued is not a failure, and
counting it would let a healthy system spend its retry budget on politeness. The
next tick is fifteen minutes away and a run takes about eight.

**The container's uid is pinned to 1000.** Bind mounts arrive with the host's
ownership no matter what the image chowned, so the uid inside has to match the
host directories. `useradd -r` picks an arbitrary system uid — it picked 999 —
and every write inside the container was denied, which surfaces as `claude`
producing nothing at all rather than as a permissions error. `run.sh` checks
writability before it starts, `healthcheck.sh` compares the directory owner to
the image's `User`, and the deploy fixes or names the mismatch.

**Only the agent directories may be chowned.** One service can't vary its mounts
by argument, so `data/` is mounted whole — and `data/` also holds `state/` and
`cron.log`, which the *host* writes. `chown -R 1000:1000 data` therefore breaks
cron's own append and `tick.sh`'s attempt counter, in a way that looks like the
schedule silently stopping. The deploy chowns `data/morning-briefing` and
`data/opportunities` by name, and `healthcheck.sh` fails if `state/` or
`cron.log` ever ends up owned by the container.

**One image, one service, two agents.** They're the same runtime and differ only
in the argument, so a second image would double CI time and pull bandwidth for
no isolation gain. The isolation that matters — archives, schedules, attempts,
locks — lives outside the image entirely.

**Ephemeral container, not a scheduled service.** `tick.sh` runs
`docker compose run --rm`. No cron daemon in the image, no supervisor, nothing
to keep alive — and the thing cron runs is exactly the thing you can run by
hand with `./tick.sh <agent> --force`. `profiles: [cron]` keeps a stray
`docker compose up -d` from firing a brief as a side effect of poking at the
box.

**Compose supplies the environment.** The classic cron failure — empty `PATH`,
missing tokens — doesn't apply, because `env_file: [.env]` is read by Compose
rather than inherited from cron. The installed entry only needs an absolute path
to `docker`.

## Troubleshooting

**Nothing arrives.** Run `./healthcheck.sh` first — it covers everything below
in one pass, per agent, and tells you which layer broke. Then `data/cron.log`
for the scheduling side and `data/<agent>/logs/<date>.json` for the run itself.
On failure `run.sh` logs a `FAILED` line plus the first 500 characters of
Claude's result. Every line in `cron.log` carries its agent in brackets, so
`grep '\[opportunities\]' data/cron.log` separates the two.

Note that `grep FAILED` alone can hide the answer: Claude's stderr is written
above that line, not after it. Read the surrounding context, not just the match.

**It runs but nothing is produced, in zero seconds.** The bind mount is owned
by the wrong uid, so the shell cannot even create the log file and `claude`
never starts. `run.sh` catches this up front now; if you see it, run the
`chown` from step 5 above. This failure reads exactly like a model failure and
is not one.

**cron stopped firing, or attempts never increment.** The mirror image of the
above: something chowned `data/` recursively and handed `data/state` or
`data/cron.log` to the container's uid, so the *host* can no longer write them.
`healthcheck.sh` reports this explicitly. Give those two back to your own user.

**It never fires at all.** `./tick.sh <agent> --dry-run` says which gate stopped
it — agent disabled, wrong day, hour not reached, brief already written, or
attempts exhausted. If it says it *would* run, the problem is downstream of the
schedule.

**It fires at the wrong hour.** Check `TZ` in `.env`, not the box. The host
timezone has no effect; a Berlin box serving a Jakarta reader is correct by
design.

**One agent runs and the other doesn't.** Check `OPPS_ENABLED` first — it is `0`
by default. If both are enabled and one is consistently late, check whether they
share an hour: the second waits for the first to finish and starts on a later
tick, by design.

**It gave up for the day.** After `_MAX_ATTEMPTS` failures `tick.sh` stops
retrying so a broken run can't burn your usage limits until midnight. Fix the
cause, then `./tick.sh <agent> --force`. Attempts are counted per agent.

**It stops working after weeks of running.** The OAuth token expired. Re-run
`claude setup-token`, update the `CLAUDE_CODE_OAUTH_TOKEN` secret, and redeploy
— check this before debugging anything else. One token serves both agents, so
they stop together.

**It's eating your usage limits.** A 30–40 turn research run is a real chunk of
a Pro budget and competes with your own Claude Code usage — and there are now
two agents drawing on it. Compare `total_cost_usd` in each agent's logs to see
which one is expensive before cutting either. Lower `BRIEFING_MAX_TURNS` or
`OPPS_MAX_TURNS`, drop the matching `_EFFORT` to `low`, or thin the schedule
(`BRIEFING_DAYS=1,3,5`, `OPPS_DAYS=1`). If it's still tight, the ladder is Max,
or API billing with `ANTHROPIC_API_KEY`.

**The briefing is padded or repetitive.** Tighten the "Watching for" lines in
`watchlist.md` and extend the "Not interesting" list. That fixes it far more
reliably than editing `prompt.md`.

**The opportunities brief finds something every time.** That's the failure mode
it's built to avoid, and it means the filter is too loose rather than the market
being interesting. Make the "Would need" lines in `universe.md` concrete — a
multiple, a drawdown, a resolved overhang — and move anything vague to the
"Never" list with the reason.

**`docker compose pull` fails on the box.** The GHCR package is private by
default and is a *different* package from the old `thesis-server` one. Either
make it public, or `docker login ghcr.io` with a PAT carrying `read:packages`.

## The opportunities brief

Off by default. Turn it on by setting `OPPS_ENABLED=1` and redeploying — its
cron entry is already installed, so nothing else changes.

Before you do, fill in `agents/opportunities/universe.md` and run it locally a
few times. It's a different tuning problem from the morning briefing: that one
is about filtering a firehose, this one is about *not* producing output. Three
things it's built to do, all of which are worth checking in the first few runs:

- **Stay quiet.** Over a few days on a multi-year horizon, usually nothing
  changes. The prompt says so explicitly and permits a near-empty brief. If
  yours is full every time, the universe is too loose.
- **Name the bear case.** Every candidate must carry the strongest argument
  against it, found by searching for one on purpose. An item without it is a
  prompt failure, not a quiet market.
- **Say "unverified".** Multi-year valuation history is the figure free web
  research most often can't confirm. Saying so is the correct output; a
  confident number that was inferred is not.

It reports; it does not advise. No price targets, no entries, no urgency — the
brief describes a situation and what the market appears to believe about it, and
you decide what to do.

## Cost

On a Claude Pro subscription: **$0 marginal** — both agents draw on usage limits
rather than per-token billing. `data/<agent>/logs/<date>.json` records
`total_cost_usd` per run, so you can see what an equivalent API run would have
cost, and which agent is the expensive one, if you ever switch to
`ANTHROPIC_API_KEY`.
